# Первая SQL-миграция HandyCraft

## Что проверено

Код взят из `fogetfully/HandyCraft`, ветка `main`, коммит
`2fa22aa2f5a1df1549f15ace294c6b24c868aa24` (проверка 22 ноября 2026).
Источники схемы: `HandyCraft_2026-11-18T18_22_50.033Z.sql`,
`HandyCraft_2026-contracted.json`, `handycraft-openapi.yaml`.

SQL использует диалект **PostgreSQL** (`serial`, двойные кавычки,
`COMMENT ON COLUMN`). В ER-файле указано `database: generic`: он сам по себе
не определяет СУБД. SQL содержит только DDL, без данных и версии сервера;
это ошибочный экспорт модели, а не подтверждённая схема работающей базы.
К существующей базе в ходе этой работы подключений не было.

В актуальном Go-коде `storage.New(nil, cfg)`, запросов к БД нет.
`sqlx` — обёртка для работы с SQL, а не драйвер конкретной СУБД.
`DATABASE_URL` читается, но не используется для подключения. В Compose
нет базы; Dockerfile запускает только приложение. Go-код и зависимости
этой миграцией не изменены.

## Исправления в 000001

Сохранены все 11 таблиц, 87 столбцов, их имена, типы (кроме ошибочного
`text(65535)`), nullable-поля, значения по умолчанию и правила `NO ACTION`.

| Ошибка экспорта | Исправление |
| --- | --- |
| `CHECK(Role ...)` при столбце `"Role"` | Кавычки во всех CHECK: регистр имён теперь совпадает |
| `COMMENT ON COLUMN Posts.Type` | `COMMENT ON COLUMN "Posts"."Type"` |
| `text(65535)` в четырёх столбцах | PostgreSQL `text`; лимиты API — отдельное решение |
| `Messages.MessageID → Images.MessageID` | `Images.MessageID → Messages.MessageID`: много изображений у сообщения |
| `CREATE TABLE IF NOT EXISTS` | Обычный `CREATE TABLE`: существующая таблица должна выявить конфликт |
| Частично выполненный экспорт при ошибке | Явная транзакция `BEGIN` / `COMMIT` |

У ошибочного FK целевой `Images.MessageID` не уникален. Добавлять ему
`UNIQUE` нельзя: API допускает несколько картинок у одного сообщения.
В ER эта связь нарисована как `one_to_many` от Messages к Images;
SQL-экспорт неверно перенёс её направление в FOREIGN KEY.

Справка PostgreSQL: [имена и кавычки](https://www.postgresql.org/docs/current/sql-syntax-lexical.html),
[строковые типы](https://www.postgresql.org/docs/current/datatype-character.html),
[ограничения и внешние ключи](https://www.postgresql.org/docs/current/ddl-constraints.html).

## Расхождения с API, которые ещё нужно решить

Эта миграция создаёт исправленную исходную схему. Она не означает, что
backend уже реализует API или что все бизнес-правила обеспечены базой.

| Область | Состояние и следующий шаг |
| --- | --- |
| Пароль | `password varchar(50)` недостаточен для многих форматов хеша. Перед реализацией регистрации расширить поле до `text` или подходящего `varchar`, хранить только хеш. Лимит пароля из API относится к вводу, а не хешу |
| Авторизация | Нет хранилища refresh-токенов, подтверждений email и сброса пароля. Выбрать схему хранения и отзыва токенов отдельным изменением |
| Время | `timestamp` не хранит часовой пояс, API использует UTC. Выбрать UTC-соглашение или `timestamptz`; для существующих данных сначала установить их исходный часовой пояс |
| Идентификаторы | `serial/int` — 32 бита, в OpenAPI встречается `int64`. Это меньший допустимый диапазон, а не немедленная ошибка; переход на bigint требует согласованного изменения PK и FK |
| Публикации | База допускает active без Title; не обеспечивает соответствие Products/Orders типу Posts и обязательный quantity у активного товара. Это потребует CHECK и/или транзакционной логики приложения |
| Длина текста | API ограничивает description 5000, комментарии и отзывы 2000, сообщения 4000 символами. `text` этих лимитов не проверяет |
| Комментарии | FK ParentID не проверяет принадлежность родителя той же публикации. API требует эту проверку. Удалённый комментарий с ответами должен оставаться заглушкой |
| Диалоги и отзывы | LastMessageID может указывать на чужой диалог; SenderID/AuthorID/SubjectID не проверяют участие в нём. Не обеспечены запрет отклика на свою публикацию/идею и отзыв только после двух подтверждений |
| Изображения | Не ограничено одновременное заполнение PostID и MessageID, принадлежность загрузившему, количество и порядок вложений. Удаление файлов из хранилища также требует логики приложения |
| Удаление | API описывает каскадные эффекты и мягкое удаление, SQL везде использует NO ACTION. `ON DELETE CASCADE` не сработает при UPDATE deleted; стратегию удаления нужно реализовать согласованно |
| Лайки/закладки | Уникальность есть. После мягкого удаления повторный INSERT той же пары конфликтует: восстановить запись либо выбрать другую стратегию удаления. Операции PUT должны быть идемпотентны |
| Счётчики | LikesCount, CommentsCount и unread-счётчики не обновляются автоматически. Нужна транзакционная логика записи/чтения |

В самом OpenAPI обязательность `title`/`quantity` при active описана текстом,
но не выражена условными схемами. `MessageCreate` допускает `imageIds: []`
без content через `anyOf`; это не обеспечивает требование непустого сообщения.
Эти места стоит уточнить при реализации соответствующих обработчиков.

## Безопасный порядок

1. Для новой пустой базы применить `000001_initial_schema.up.sql`.
   `up` создаёт таблицы, затем связи. При ошибке транзакция откатывается целиком.
2. Если база уже существует, сначала сделать резервную копию и проверить её
   восстановление в отдельную базу. Сравнить фактическую схему с миграцией.
   Не запускать 000001 поверх данных и не скрывать расхождения через IF NOT EXISTS
   или принудительную установку версии. Для отличий нужна отдельная ALTER-миграция.
3. Проверить ограничения на тестовых данных, затем выполнить `down`, затем `up`.
4. Только после этого выбирать следующую небольшую миграцию под конкретный
   обработчик. Применённые миграции не редактировать: добавлять следующий номер.

`down` здесь намеренно работает только для пустых таблиц. Сначала он блокирует
все 11 таблиц, проверяет отсутствие строк, затем удаляет их одной командой
без CASCADE. Строки с `deleted` тоже считаются данными. Внутренние циклы
Users/Images и Dialogs/Messages допустимы при совместном удалении таблиц.
Внешняя зависимость останавливает откат. Ограничено время ожидания блокировок.
Откат схемы не заменяет восстановление данных из резервной копии.

## Проверка через Docker на Windows

Из каталога `backend`, при запущенном Docker Desktop:

```powershell
./scripts/test-migrations.ps1
```

Из корня репозитория тот же сценарий запускается командой
`./backend/scripts/test-migrations.ps1`. Все файлы миграций и их проверки
находятся внутри `backend`; тестовый Compose-файл — `backend/compose.migrations-test.yml`.

Сценарий создаёт отдельный Compose-проект со случайным именем и PostgreSQL 17,
без открытых портов и постоянных томов. Через `golang-migrate` v4.20.1 он делает:

```text
up 1 → проверки SQL → down 1 → проверка пустой схемы → up 1 → проверки SQL
```

Тестовые INSERT выполняются в транзакции с ROLLBACK. После проверки тестовый
проект удаляется даже при ошибке. Рабочий docker-compose.yml не используется.
Пароль в тестовом Compose предназначен только для этой одноразовой базы.

Для вручную подготовленной **пустой учебной базы**, из каталога backend,
при установленном [golang-migrate CLI](https://github.com/golang-migrate/migrate/tree/v4.20.1/cmd/migrate):

```powershell
migrate -path ./migrations -database $env:DATABASE_URL up 1
migrate -path ./migrations -database $env:DATABASE_URL version
# Только для отката пустой учебной базы:
migrate -path ./migrations -database $env:DATABASE_URL down 1
```

Не направляй учебные команды на действующую базу. Миграции запускаются отдельно
от HTTP-сервера; подключение Go к БД будет следующим этапом.

После ошибки `golang-migrate` может оставить версию в состоянии `dirty`,
даже если SQL-транзакция откатилась (например, сработала защита down).
Сначала прочитать ошибку, убедиться в откате транзакции и проверить фактическую
схему. Не выполнять `force` автоматически: он меняет только запись о версии,
не исправляет таблицы и не восстанавливает данные.

## Результат выполненных проверок

- Исходный `go test ./...` прошёл; в репозитории пока нет Go-тестов.
- На PostgreSQL 18.7 в PGlite 0.5.17 успешно выполнены up/down/up,
  сравнение схемы после повторного up, тестовые связи и ограничения.
- Проверены отказ down при наличии данных, сохранность данных после отказа,
  отказ при внешней зависимости, отказ повторного up и атомарность при
  конфликте с уже существующей таблицей.
- Имена 11 таблиц и 87 столбцов, nullable-поля и количество 22 связей
  сопоставлены с ER-файлом. Направление Images → Messages исправлено осознанно.
- PowerShell-сценарий разобран парсером, Compose-файл прошёл `config --quiet`.
- Полный запуск Docker + PostgreSQL 17 + golang-migrate пока **не выполнен**:
  Docker engine в текущей среде недоступен. Проверка PGlite проверяет SQL,
  но не контейнеры, сетевое подключение или учёт версий в golang-migrate.
